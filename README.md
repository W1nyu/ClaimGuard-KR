# ClaimGuard-KR

**사람 검토와 AI 위험평가를 갖춘 보험금 청구서류 접수 자동화**

📄 한 장 요약 페이지: https://claude.ai/artifact/7QR5eQEP7ShAT5PUbrWg6M

💡 인사이트 한 장: https://claude.ai/artifact/GkY2kk6gv5XGvm7y3M5fmi

DB손해보험 양식 보험 서류(AI Hub 공개 데이터, 값은 가상)를 대상으로
**서류 분류 → 항목 추출 → 접수 검증 → 처리 결정**을 자동화하고,
2026년 6월 개정 **「금융분야 인공지능 가이드라인」의 위험평가 체계**로 시스템 자체를 평가한 개인 프로젝트입니다.

> DB손해보험 양식의 AI Hub 공개 데이터를 사용한 개인 프로젝트이며, DB손해보험과 관련이 없습니다.

## 왜 이 문제인가

- 실손 청구 전산화(실손24) 의료기관 연계율은 28.4%(2026.4), 전체 청구 중 실손24 이용은 4.6%에 그쳐 청구 서류 대부분이 아직 종이·사진으로 접수된다.
- 접수 단계의 서류 분류·항목 입력·오기재 확인·보완 요청은 수작업 비중이 크다.
- 개정 가이드라인은 보험금처럼 계약자에게 영향이 큰 AI에 **사람의 실질적 검토, 설명, 사후 점검**을 요구하고, 위험을 점수(25/50/75점)로 등급화하는 방식을 제시했다. 보험사 중 AI 거버넌스 의사결정기구를 둔 곳은 7.5%(금감원, 2025.4)다 ([라이센스뉴스](https://www.lcnews.co.kr/news/articleView.html?idxno=208587)).

## 청구 건 단위 처리

실제 청구는 서류 한 장이 아니라 **청구서 + 동의서 + 신분증 + 의료기관 서류 (+ 위임장)** 묶음으로 들어온다.
DB손해보험 홈페이지의 [질병](https://www.idbins.com/pc/bizxpress/ct/dc/FWCUSV1301.shtm)·[상해](https://www.idbins.com/pc/bizxpress/ct/dc/FWCUSV1300.shtm) 보험금청구서류 안내(2026.9.23 확인)를 규칙표(`src/claim_docs.py`)로 옮겨, 청구 정보(유형·항목·조건)로 필요 서류를 만들고 빠진 서류를 **발급처와 함께** 안내한다.

- 50만원 이하 입원은 진단서 대신 입퇴원확인서·진료확인서 인정, 비급여·도수치료는 진료비세부내역서 필수, 상해는 사고 원인별 입증서류(교통사고 사고사실확인서, 산재 요양급여신청서 등)
- 청구서의 **예금주 ≠ 피보험자**이면 위임장·청구권자 동의서·인감증명서를 자동으로 필요 서류에 추가
- 같은 건에 위임장이 있으면 **수임인 = 예금주, 수령 계좌, 피보험자, 사고일**을 대조 (B02~B05)
- 청구 화면에서 **제출 전에** 빠진 서류를 미리 보여준다
- 의료기관·관공서 서류는 공개 데이터에 이미지가 없어 서류 종류만 받고 내용은 읽지 않는다

**평가에서 드러난 설계 문제와 보정** (`results/eval_bundle.csv`)

| | 보정 전 | 보정 후 |
|---|---|---|
| 서류 간 대조 | 내용이 일치하는 쌍에서도 OCR 오류로 **24~58%가 거짓 불일치** → 고객에게 잘못된 보완요청 | 불일치는 **담당자 원본 확인**으로 (고객에게 바로 가는 거짓 불일치 0건) |
| 위임 서류 자동 요구 | 오인식된 이름으로 위임 서류를 잘못 요구할 수 있음 | 이름 확신도가 높을 때만 자동 추가 → 177건 중 102건 자동, 75건 담당자 확인 |

로컬 OCR(위임장 칸 일치율 69.8%)로는 서류 간 자동 대조를 고객 응대에 직접 쓸 수 없다는 것을 수치로 확인하고, 사람 확인 단계로 돌렸다.

> **정정 (정답 라벨 보정 후)**: 이전에는 "예금주 = 피보험자인 14건 모두에 위임 서류를 잘못 요구했다"고 적었다. 확인해 보니 이 14건은 예금주·피보험자 칸에 글씨가 있는데 **정답 라벨이 빠진 서류**였다. 라벨이 있는 177건은 모두 예금주 ≠ 피보험자라, 이 데이터로는 위임 서류를 잘못 요구하는 비율을 잴 수 없다. 확신도 기준은 이름 오인식에 대한 안전장치로 유지하되, 효과는 검증되지 않은 상태다.

**담당자 검토 흐름**: 담당자로 넘어간 청구 건은 '청구 검토' 화면에서 원본 이미지를 보며 ① OCR 오류는 값을 고치고 ② 맞는 값은 '확인'으로 표시하고 ③ 위임 여부를 판단하고 ④ 원본에서도 다른 불일치는 '실제 불일치'로 확정해 고객 보완요청으로 돌린다. 재판단은 OCR을 다시 돌리지 않고 담당자가 확인한 값으로 계산하며, 모든 수정·판단·확정은 감사 로그에 남는다.

**보완 → 재제출 순환**: 청구 건의 상태는 결정에 따라 접수완료 / 보완대기 / 검토대기로 나뉜다. 보완대기 건에 고객이 빠진 서류를 추가로 내면(청구 접수 화면의 '보완 서류 제출') 같은 건에 붙여 다시 판단하고, 회차마다 낸 서류·해결된 누락·남은 누락을 기록한다. 고쳐서 다시 낸 청구서·위임장은 이전 것을 대신하며, 이전 값으로 한 담당자의 불일치 확정은 무효가 된다. 이로써 접수 → 자동 판단 → 담당자 검토 → 보완 → 재접수 → 접수완료의 흐름이 한 건 안에서 이어진다.

구양식 청구서(15)에는 예금주 칸이 없어 위임 자동 판단과 위임장 대조를 하지 않는다.

**처리 결정** (엔진 A, 400장)

- 잘못된 자동접수(정답은 문제가 있는데 자동접수): **0건**
- 확신도 기준 0.85를 적용하면 사실상 전 건 담당자검토 → 현재 정확도에서는 "자동화"보다 "담당자 보조"가 맞다.
- 규칙별 결정 일치율(정답 값 vs OCR 값): R08 진단명 74%, 나머지 90% 이상 (`results/eval_rules.csv`).

**빈칸 오인식 개선: 잉크 판단** (엔진 A, 400장, `results/eval_decisions.csv`)

필수 칸 R01의 낮은 일치율(보정 전 62~69%)은 두 원인이 섞여 있었다. ① 정답 라벨이 빠진 칸(위 표) ② OCR이 짧은 손글씨 숫자('1', '11')를 빈 글자로 돌려준 칸. ②를 다시 읽는 방법(글씨 부분만 잘라 여백 추가·확대, 칸 선 제거)도 시험했지만 144칸 중 12칸만 맞고 112칸은 **틀린 값**을 냈다. 틀린 값은 빈칸보다 위험하므로 다시 읽지 않고, **글씨가 있는데 비었으면 '읽지 못함'으로 담당자에게 넘긴다(R12).** 그 칸 때문에 실패한 날짜·주소 규칙도 고객에게 보내지 않고 보류한다.

**진단명 매칭 개선** (엔진 A 청구서(신) 191장, 진단명이 KCD에 정확히 없는 OCR 값)

- 이 데이터의 진단명 정답은 거의 모두 KCD 공식 명칭이라, R08 불일치의 대부분은 '공식 명칭만 매칭'이 아니라 **OCR 한두 글자 오류**(치밀골염 → 치밀골영, 구리결핍 → 구리얼집)였다.
- 한글을 자모로 풀어 비교하니 받침·모음 하나 차이가 거리 1이 된다. 담당자에게 보여주는 **1순위 후보가 정답인 비율이 4%(45건 중 2건) → 82%(37건)**, 엔진 B는 10건 중 0건 → 8건.
- 자모 거리 1·후보 하나일 때 자동 보정하면 31건 중 29건이 정답과 같았고(1건은 정답 자체가 KCD에 없는 이름), 1건은 **다른 병**이었다(케산병을 엔진 B가 '계산병'으로 읽어 고산병으로 보정). 진단명은 지급 판단에 쓰이므로 자동 통과시키지 않고 **보정안을 담당자에게 제시**한다.
- 흔히 쓰는 이름은 사전(`config/diagnosis_synonyms.json`, 18개)으로 공식 명칭에 연결한다(유방암 → 유방의 악성 신생물 C50, 허리디스크 → 기타 추간판장애 M51). 뜻이 여러 분류에 걸치는 이름(폐렴, 대장암)은 넣지 않았다. 이 데이터에는 흔히 쓰는 이름이 거의 없어 사전의 효과는 측정하지 못했다.

**AI 위험평가** (가이드라인 예시표, 수행률은 작성자 판단 + 측정 근거)

| 시나리오 | 총 잔여 위험 | 등급 | 가장 큰 차이 |
|---|---|---|---|
| 엔진 A + 담당자 검토 | 27.4점 | 중위험 | — |
| 엔진 B + 담당자 검토 | 43.8점 | 중위험 (고위험 근접) | 보안성 5.4 → 18.6 (외부 전송, 위탁, 사용량 한도 장애) |

## 발견한 것

1. **평가 기준부터 의심해야 한다.** 가장 약하다고 본 규칙(R01)의 오류 약 3분의 1(일치율 68.9% → 80.4%, 62.3% → 74.3%)과 엔진 B의 R01 오류 전부가 엔진이 아니라 정답 라벨 누락 때문이었다. 칸 안의 잉크만 봐도 찾을 수 있었다.
2. **틀린 값보다 '모름'이 낫다.** 못 읽은 칸을 다시 읽으면 대부분 틀린 값이 나왔다. 읽지 못했다고 표시하고 사람에게 넘기자, 고객에게 가던 거짓 누락 요청이 90장에서 0장이 됐다.
3. **보정이 맞을 확률이 높아도 결정은 사람이 한다.** 진단명 자동 보정은 31건 중 29건이 정답과 같았지만 1건은 다른 병이었다. 후보 제시로 담당자 일은 줄이고 확정은 맡기지 않았다.
4. **정확한 엔진이 더 안전한 엔진은 아니다.** 엔진 B는 20%p 더 정확하지만 개인정보 외부 전송·외부 의존 때문에 위험 점수는 더 높다.
5. **언어모델 편향**: 엔진 B는 드문 성씨를 흔한 성씨로 바꿔 읽었다(곡→곽, 뢰→최, 묘→표). 이름 오류는 본인 확인·지급 오류로 이어질 수 있다.
6. **외부 의존 장애를 실제로 겪었다**: 일괄 추출 중 구독 사용량 한도로 100장 중 15장이 실패했다. 엔진 A 자동 대체 경로를 둔 근거.
7. **평가 지표를 정직하게**: 데이터 값이 무작위라 거의 모든 서류가 여러 규칙을 위반한다. 전체 결정 일치율(92~99%)은 부풀려진 수치라 규칙별 일치율을 함께 본다. 금액 칸의 "원"·쉼표 표기 차이는 두 엔진 모두 숫자만 비교하도록 보정했다.

## 한계

- 데이터 값이 가상이라 자동접수 비율, 실제 사기·지급 판단은 측정할 수 없다. 진료비 영수증은 공개 데이터가 없어 다루지 않았다.
- 체크박스(상해/질병/교통사고 등)는 라벨이 없어 제외했다. 청구서 외 6종은 분류만 한다.
- 흔히 쓰는 진단명 사전은 18개뿐이고, 직업(KSCO)에는 사전이 없다. 사전에 없는 이름은 담당자검토로 넘긴다.
- 읽지 못한 칸은 사람이 채워야 한다. 짧은 손글씨 숫자(월·일)를 읽는 문제 자체는 모델을 바꾸거나 학습하지 않으면 풀리지 않는다.
- 위험평가 수행률은 작성자 한 사람의 판단이다. 독립 검증, 고객 이의제기 절차, AI 활용 고지는 구현하지 않았다.
