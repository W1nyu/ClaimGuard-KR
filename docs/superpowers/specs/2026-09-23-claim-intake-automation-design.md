# 설계서: DB손해보험 청구서류 접수 자동화 + AI 위험평가

- 작성일: 2026-09-23
- 목적: 보험사 백오피스(디지털·IT) 직무 지원용 포트폴리오 프로젝트
- 기간: 5주
- 대상 사용자: 보험금 청구 접수 담당자 (시연용)

## 1. 배경과 목표

실손24 의료기관 연계율은 28.4%(2026.4), 전체 실손 청구 중 실손24 이용은 4.6%에 그쳐 청구 서류 대부분이 아직 종이·사진으로 들어온다. 접수 단계에서 서류 분류, 항목 입력, 오기재 확인, 보완 요청이 수작업으로 이뤄진다.

또한 2026.6 개정 「금융분야 인공지능 가이드라인」은 보험금 지급처럼 계약자에게 영향이 큰 AI에 대해 사람의 실질적 검토, 설명, 사후 점검을 요구하고, AI 위험평가 결과를 점수(25/50/75점)로 등급화하는 방식을 제시한다.

**목표**
1. DB손해보험 실제 양식 서류에서 항목을 자동 추출하고, 접수 규칙으로 검증해 처리 방향(자동 접수 / 보완 요청 / 담당자 검토)을 결정한다.
2. 무료 로컬 OCR과 VLM(Claude)을 같은 기준으로 비교해 정확도·속도·외부 전송 위험의 트레이드오프를 수치로 제시한다.
3. 금융분야 AI 가이드라인의 위험평가 체계로 이 시스템 자체를 평가하고, 사람 검토·감사 로그 같은 통제를 시스템에 구현한다.

**범위 밖**
- 보험금 지급액 산정, 사기 판정 (데이터 값이 무작위라 불가)
- 체크박스 인식 (라벨 없음)
- 청구서 이외 6종 서류의 항목 추출 (서류 분류만 8종 전부 수행, 시간이 남으면 확장)
- 실제 운영 배포, 로그인·권한 관리

## 4. 구성 요소

### 4.1 load_data.py
- zip을 풀지 않고 파일 목록·이미지·라벨 JSON을 읽는다.
- 반환: `(이미지 PIL, 라벨 dict, 양식 코드, 분할(train/val))`.

### 4.2 form_templates.py + 정답 생성
- 청구서 2종(15, 16)에 대해 칸 이름 → 사각형 좌표 표를 파이썬 dict로 정의한다.
- 초안 생성: Training 라벨 박스 중심 좌표를 양식별로 모아 군집화 → 칸 후보 사각형. 이미지에 겹쳐 그린 검수 이미지를 만들어 사람이 확인·수정한다.
- `build_ground_truth.py`: 라벨 박스 중심이 속한 칸에 값을 넣는다. 한 칸에 박스가 여러 개면 x 좌표 순으로 공백 연결. 어느 칸에도 속하지 않은 박스 수를 보고한다(칸 위치 품질 지표, 목표 1% 미만).
- 날짜처럼 여러 칸으로 나뉜 값(년/월/일/시/분)은 칸별로 두고, 검증 단계에서 합친다.

청구서(신, 16) 칸: 피보험자_성명, 주민번호, 회사명, 부서명, 직업, 주소_시도, 주소_시군구, 주소_도로명, 주소_번지, 보상안내_성명, 보상안내_관계, 연락처, 이메일, 타사보험1~3, 사고_년, 사고_월, 사고_일, 사고_시, 사고_분, 진단명, 사고장소, 치료병원, 사고경위, 계좌번호, 은행명, 예금주, 작성_년, 작성_월, 작성_일, 청구권자.

청구서(구, 15) 칸: 보험종목, 증권번호, 계약자, 가입금액, 타사보험회사, 타사가입금액, 사고일자, 사고시각, 사고원인, 사고장소, 피해품, 사고경위, 청구_년, 청구_월, 청구_일, 청구인_성명, 이메일, 관계, 주소_시도, 주소_시군구, 주소_도로명, 주소_번지, 연락처.

최종 칸 목록은 검수 이미지 확인 후 확정한다.

### 4.3 classify.py
- 이미지 상단 30% 영역을 OCR해 제목 키워드로 8종을 판별한다(예: "자동이체신청서", "간병인", "도난", "위임장", "승계 동의서", "합의서", "보험금 청구서"). 청구서 구/신은 "1. 보험계약사항"(구)과 "1. 인적 사항"(신) 문구로 구분한다.
- 판별 실패 시 `미분류`로 담당자 검토.

### 4.4 extract_paddle.py (엔진 A, 무료·로컬)
- PaddleOCR 한국어 모델로 글자 박스를 얻고, 박스 중심으로 form_templates의 칸에 배정한다.
- 칸별 확신도 = 해당 칸 박스들의 OCR 점수 최솟값.

### 4.5 extract_claude.py (엔진 B, 구독)
- Claude API는 사용하지 않는다.
- 평가: Claude Code 세션에서 이미지를 읽고 칸 목록에 맞춘 JSON을 `data/processed/claude_outputs/<id>.json`으로 저장한다. 100장을 여러 번에 나눠 처리하고, 건당 소요 시간을 기록한다.
- 시연: 앱에서 로컬 `claude -p` CLI를 subprocess로 호출해 1장을 처리한다. CLI가 없거나 실패하면 엔진 A로 대체하고 화면에 표시한다.
- 입력 이미지는 긴 변 1600px로 줄인다.

### 4.6 reference.py
- KCD-9: 한글명칭 → 코드. 정확 일치 → 공백 제거 일치 → 유사도(difflib) 0.8 이상 순으로 찾고, 결과에 일치 방식을 표시한다. 최하위코드만 대상으로 한다.
- KSCO 8차: PDF에서 5자리 세세분류 코드와 한글명을 뽑아 CSV로 캐시한다. 직업명 매칭은 KCD와 같은 방식이다. 색인어(흔히 쓰는 직업명)는 없으므로 실패하면 담당자 검토.
- 은행: 금융회사코드 파일을 CP949로 읽고, 앞 3자리 코드별 은행명(전각 문자 정규화)을 목록으로 만든다.
- 도로명주소: API로 조회하고 결과를 `data/processed/juso_cache.json`에 저장한다(같은 주소 재조회 방지). 키 만료·네트워크 오류 시 "확인 불가"로 담당자 검토.

### 4.7 validate.py
각 규칙은 `(규칙ID, 결과: 통과/위반/확인불가, 대상 칸, 사유 문장, 처리: 보완요청/담당자검토/추가서류)`를 반환한다.

| ID | 규칙 | 위반 시 처리 |
|---|---|---|
| R01 | 필수 칸 누락 | 보완요청 |
| R02 | 날짜 실재 여부 (연 1900~올해, 월·일 유효) | 보완요청 |
| R03 | 사고일 ≤ 작성일 ≤ 오늘 | 보완요청 |
| R04 | 사고일로부터 3년 초과 (상법 제662조 소멸시효) | 담당자검토 |
| R05 | 주민번호 형식(6-7자리), 생년월일 실재, 성별자리 1~8 | 보완요청 |
| R06 | 연락처·이메일 형식 | 보완요청 |
| R07 | 주소 실재 (도로명주소 API) | 보완요청 |
| R08 | 진단명 → KCD-9 매칭 실패 | 담당자검토 |
| R09 | 직업 → KSCO 매칭 실패 | 담당자검토 |
| R10 | 은행명 실재, 계좌번호 숫자 10~14자리 | 보완요청 |
| R11 | 예금주 ≠ 피보험자(신) / 청구인(구) → 위임장·인감증명서 필요 | 추가서류 |

양식별로 존재하는 칸에 해당하는 규칙만 적용한다.

### 4.8 route.py
- 우선순위: 담당자검토 사유가 하나라도 있거나, 칸 확신도가 기준값(기본 0.85) 미만이면 → **담당자 검토**. 그 외 보완요청·추가서류 사유가 있으면 → **보완 요청**(고객 안내 문구 생성). 모두 통과면 → **자동 접수**.
- 고객 안내 문구는 규칙 사유 문장을 템플릿으로 조합한다(LLM 사용하지 않음).
- 결정마다 사유 목록을 함께 반환한다(설명 가능성).

### 4.9 audit.py
- SQLite `data/processed/audit.db`. 테이블: `decisions`(서류ID, 시각, 주체 AI/담당자, 엔진, 결정, 사유 JSON), `edits`(서류ID, 칸, 이전값, 새값, 수정자, 시각).
- 담당자가 값을 고치면 검증·결정을 다시 실행하고 새 결정을 기록한다.

### 4.10 risk_assessment.py (H)
- 가이드라인 본문 13~14쪽 방법과 15쪽(인쇄 쪽번호 13) 예시표를 따른다. 항목별 배점(=만점 위험)에 대해 경감 수행률을 입력하면 잔여 위험 = 배점 × (1 − 수행률) (14쪽: "30% 수행 시 잔여위험은 배점의 70%").
- 예시표 항목과 배점 (원문 그대로, 총 배점 100):

| 원칙(비중) | 항목: 배점 |
|---|---|
| 합법성(20%) | 금융소비자보호법 위반 가능성 8, 인공지능기본법 위반 가능성 4, 데이터 관련법 위반 가능성 4, 개별 업권법 위반 가능성 4 |
| 신뢰성(30%) | 품질 6, 편향성 6, 공정성 6, 설명가능성 6, 성능 6 |
| 신의성실(20%) | 계약 권리 침해 6, 책임 투명성 6, 소비자 보호 방안 8 |
| 보안성(30%) | 보안 8, 안정성 8, 위탁·관리 8, 프라이버시 6 |

- 원문 예시의 잔여 위험 합계는 54점(고위험)이다. 이 값으로 계산 로직을 테스트한다.
- 총 잔여 위험 합계로 등급: 25 미만 저위험, 25~50 미만 중위험, 50 이상 고위험, 75 이상 의사결정기구 재검토.
- 항목과 배점은 코드 안 표(dict)로 두고 원문 쪽수를 주석으로 단다.
- 기본 시나리오 2개: "엔진 A(로컬) 사용"과 "엔진 B(외부 모델) 사용". 외부 전송·외부 모델 의존 항목 점수가 달라져 등급 차이를 보여준다.
- 결과를 Markdown 보고서로 내보낸다.

## 5. 화면 (Streamlit)

1. **서류 접수**: 검증 데이터에서 선택하거나 업로드 → 분류 결과 → 이미지 위 칸 박스와 추출값 → 규칙 결과표 → 처리 결정·사유·고객 안내 문구. 엔진 선택(A/B).
2. **검토 대기함**: 담당자 검토 건 목록 → 값 수정·승인 → 재검증, 수정 이력 기록.
3. **성능 비교**: 엔진별 칸 정확도, 글자 오류율, 분류 정확도, 처리 시간, 결정 일치율 표·그래프 (`results/`의 평가 결과를 읽음).
4. **AI 위험평가**: 항목별 수행률 입력 → 점수·등급·필요 통제 → 보고서 다운로드. 기본 시나리오 2개 비교.
5. **감사 로그**: 결정·수정 이력 조회.

## 6. 평가

- 대상: Validation 청구서 400장 (엔진 A 전체, 엔진 B는 양식별 50장씩 100장). 서류 분류는 Validation 전체 1,598장.
- 지표
  - 칸 단위 완전 일치율 (공백 제거 후 비교)
  - 글자 오류율 (CER)
  - 서류 분류 정확도
  - 건당 처리 시간
  - **결정 일치율**: 정답 값으로 돌린 검증·결정과 추출 값으로 돌린 결과가 같은 비율. 규칙별 불일치도 집계
  - 칸 배정 실패율 (정답 생성 품질)
- 무작위 값 때문에 자동 접수 비율은 성과 지표로 쓰지 않는다. 이 점을 결과 문서에 명시한다.
- 결과는 `results/eval_summary.csv`와 그래프 PNG로 저장한다.

## 7. 오류 처리

- 이미지 읽기 실패, OCR 실패 → 해당 건 `미처리`로 기록하고 담당자 검토.
- 외부 조회(도로명주소) 실패 → 규칙 결과 `확인불가`, 담당자 검토. 앱은 멈추지 않는다.
- Claude CLI 실패·시간 초과(60초) → 엔진 A로 대체, 화면과 감사 로그에 표시.

## 8. 테스트
