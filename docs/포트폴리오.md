# 포트폴리오: ClaimGuard-KR

사람 검토와 AI 위험평가를 갖춘 보험금 청구서류 접수 자동화 · https://github.com/W1nyu/ClaimGuard-KR

지원 직무: 보험사 디지털·IT 백오피스
기간: 5주 (개인 프로젝트)
기술: Python, PaddleOCR, Claude(구독 CLI), SQLite, Streamlit, pytest

## 1. 한 줄 요약

DB손해보험 실제 양식 약 14,400장으로 **청구서류 접수 자동화**를 만들고, 무료 로컬 OCR과 생성형 AI를 같은 기준으로 비교한 뒤, **금융분야 AI 가이드라인의 위험평가 체계로 두 방식의 위험을 점수화**했다.

## 2. 배경

- 실손24 연계율 28.4%, 이용률 4.6% → 청구 서류는 여전히 종이·사진 중심. 접수 단계(분류·입력·오기재 확인·보완 요청)가 백오피스의 큰 부담.
- 2026.6 가이드라인 개정: 보험금처럼 계약자에게 영향이 큰 AI는 사람의 실질적 검토, 설명, 사후 점검이 필요. 위험을 점수로 등급화.
- 질문: **"AI로 접수를 자동화하되, 가이드라인이 요구하는 통제를 갖추면 어디까지 맡길 수 있는가?"**

## 3. 접근

| 단계 | 한 일 | 판단 근거 |
|---|---|---|
| 데이터 | AI Hub 보험 서류 8종(모두 DB손해보험 양식) | 실제 고객 서류는 개인정보라 사용 불가 → 공개 데이터 + 공공 기준 데이터 |
| 정답 | 손글씨 박스 좌표를 군집화해 칸 위치를 찾고 항목별 정답 자동 생성 | 수작업 라벨링 없이 3,601장 정답 확보(배정 실패 0.01% 이하) |
| 분류 | 썸네일 거리 비교 | 양식이 고정 → OCR 없이 100% |
| 추출 | 엔진 A: 칸만 잘라 읽는 Zone OCR / 엔진 B: Claude | 전체 페이지 OCR은 11.7초/장이고 인쇄 글자와 손글씨가 섞임 → Zone OCR 0.7초/장 |
| 검증 | 규칙 11개 + KCD-9·KSCO·금융회사코드·도로명주소 | 형식 검사를 넘어 실무 기준 데이터와 대조 |
| 결정 | 자동접수 / 보완요청 / 담당자검토, 사유·안내문 | 설명 가능성, 사람 검토 |
| 통제 | 감사 로그, 확신도 기반 검토, 외부 모델 장애 시 대체 | 가이드라인 책임 투명성·안정성 |
| 위험평가 | 가이드라인 예시표(16개 항목, 100점)로 두 엔진 평가 | 원문 예시(54점)를 테스트로 재현해 계산 검증 |

## 4. 결과

- 서류 분류 100% (1,598장)
- 항목 추출(같은 100장): 엔진 A 64~68%, 엔진 B 85~88% 칸 완전 일치. 엔진 A는 20~40배 빠르고 외부 전송 없음.
- 잘못된 자동접수 0건. 현재 정확도에서는 확신도 기준을 적용하면 전 건 담당자검토 → **자동화가 아니라 담당자 보조가 현실적**이라는 결론을 수치로 확인.
- 위험평가: 엔진 A 27.4점, 엔진 B 43.8점(둘 다 중위험). 차이의 대부분은 보안성(외부 전송·위탁·장애).

## 5. 배운 점

1. **정확도와 위험은 다른 축이다.** 더 정확한 생성형 AI가 개인정보·외부 의존 때문에 더 위험할 수 있다. 도입 결정은 둘을 함께 봐야 한다.
2. **생성형 AI는 "그럴듯하게" 틀린다.** 드문 성씨를 흔한 성씨로 바꿔 읽었다. OCR 오류와 달리 겉보기에 자연스러워 사람이 놓치기 쉽다.
3. **외부 의존은 실제로 멈춘다.** 평가 도중 사용량 한도로 15%가 실패했다. 대체 경로를 설계에 넣은 이유를 직접 겪었다.
4. **지표를 의심해야 한다.** 전체 결정 일치율 92~99%는 가상 데이터 때문에 부풀려진 값이었다. 규칙별로 쪼개자 필수 칸 인식(62~69%)이라는 진짜 약점이 보였다.
5. **기준 데이터 매칭은 보수적으로.** 직업 유사 매칭이 "검투사→검사"를 골랐다. 틀린 확신보다 "모르겠다"가 낫다 → 정확 일치만 통과.

## 6. 예상 면접 질문

**Q. 실제 보험사에 적용한다면 무엇부터 바꾸겠나?**
A. 세 가지입니다. ① 빈칸 판별(잉크 양 기준)로 가장 약한 필수 칸 인식을 개선. ② 이름 칸은 계약 정보(증권번호로 조회한 가입자명)와 대조해 생성형 AI의 성씨 편향을 막기. ③ 외부 모델은 사내 구축형이나 개인정보 비식별 처리 후 전송으로 바꿔 보안성 점수를 낮추기.

**Q. 왜 정확한 엔진 B를 기본으로 하지 않았나?**
A. 위험평가에서 엔진 B는 43.8점으로 고위험 기준(50점)에 가깝고, 주민번호가 담긴 이미지를 외부로 보냅니다. 정확도 20%p보다 개인정보·위탁 리스크가 크다고 봤고, 엔진 B는 선택 기능으로 두되 실패 시 엔진 A로 대체되게 했습니다.

**Q. 자동화율이 0%인데 의미가 있나?**
A. 가상 데이터라 거의 모든 서류가 실제로 보완 대상이라 자동접수 비율은 측정 자체가 불가능합니다. 대신 잘못된 자동접수 0건, 확신도로 오류 칸을 골라내는 효과(확신 높은 칸 95% vs 낮은 칸 55%, 엔진 B)를 보였고, 담당자가 확신 낮은 칸만 보면 되도록 화면을 설계했습니다.

**Q. 위험평가 점수는 주관적이지 않나?**
A. 맞습니다. 수행률은 제 판단이라 항목마다 측정 근거를 붙였고, 계산 로직은 가이드라인 원문 예시(54점)를 테스트로 재현해 검증했습니다. 가이드라인도 독립 검증을 요구하므로 실제로는 개발과 분리된 조직이 평가해야 합니다.

**Q. 보험 도메인에서 새로 알게 된 것은?**
A. 보험금 청구권 소멸시효(상법 제662조, 3년), 예금주와 피보험자가 다르면 위임장·인감증명서가 필요한 점, 청구서에 직업이 필수인 이유(직업별 상해 위험등급), 질병코드(KCD)가 심사의 기준이라는 점을 규칙으로 구현하며 익혔습니다.
